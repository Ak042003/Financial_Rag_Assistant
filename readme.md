# Financial RAG Assistant

This project is a sophisticated Retrieval-Augmented Generation (RAG) system designed to answer financial queries. It leverages a hybrid retrieval strategy, combining lexical, semantic, and structured data search, with a conversational AI layer to handle ambiguity and provide accurate, source-cited answers. The system is exposed via a clean FastAPI interface and includes a simple web UI for interaction.

## ✨ Features

  * **Hybrid Retrieval:** Combines BM25 (lexical), ChromaDB (semantic), and direct Pandas DataFrame (structured) lookups for comprehensive information retrieval.
  * **Conversational Clarification:** When faced with ambiguous queries (e.g., "best funds"), the system engages in a dialogue to understand user criteria before answering.
  * **Robust Entity Correction:** Uses an advanced n-gram and fuzzy search mechanism to correct misspelled or incomplete fund names. It can also ask for user clarification when a name is ambiguous (e.g., "SBI" could be multiple funds).
  * **Self-Correcting Query Generation:** A Large Language Model (LLM) generates Pandas queries for structured data, with a built-in validation and self-correction loop to handle errors.
  * **Source-Cited Generation:** The final answer is generated by an LLM based *only* on the retrieved context, and it includes a list of the sources used to build trust and transparency.
  * **Modular Architecture:** The codebase is separated into a one-time indexing pipeline and a lightweight runtime API, with distinct components for each task.
  * **Web Interface:** A simple and clean HTML/JavaScript frontend for easy interaction with the API.

## 🏛️ Architecture Overview

The system follows a sequential, multi-stage pipeline designed to progressively refine a user's query until it is specific enough to answer accurately.

1.  **UI (Web Frontend):** The user submits a query through the `index.html` page.
2.  **API (FastAPI - `app.py`):** The query is received by the main `/query` endpoint.
3.  **Analysis (`query_analyzer.py`):** An LLM classifies the query's intent (e.g., `comparison`, `ranking`, `ambiguous`).
4.  **Clarification/Disambiguation (`clarification_generator.py`, `utils.py`):**
      * If the intent is ambiguous, a clarifying question is generated and sent back to the user.
      * If the query involves fund names, a fuzzy search runs to correct them or ask the user to disambiguate between multiple potential matches.
5.  **Retrieval (`retrieval.py`, `pandas_generator.py`):** Once the query is clear, the `RetrievalRouter` fetches context from the appropriate source:
      * **ChromaDB:** For semantic search.
      * **BM25:** For lexical (keyword) search.
      * **Pandas:** For structured data, using an LLM-generated query.
6.  **Generation (`generative_responder.py`):** The retrieved context and the original query are sent to a final LLM, which synthesizes a human-readable answer and cites its sources.
7.  **Response:** The final answer is sent back to the UI and rendered.

## ⚖️ Key Design Decisions & Tradeoffs

This project involved several key architectural decisions, each with its own tradeoffs.

### 1\. Entity Correction: Rule-Based (Fuzzy Search) vs. NLP Model (NER)

  * **Decision:** A sophisticated rule-based approach using **n-grams and fuzzy string matching** (`thefuzz`) was chosen to identify and correct fund names.
  * **Tradeoff:**
      * **Pros:** This method is extremely **fast**, **computationally cheap**, and **highly explainable**. It requires **no training data**, which significantly reduced development time and complexity. For the well-defined problem of matching fund names, it provides excellent accuracy.
      * **Cons:** A dedicated Named Entity Recognition (NER) model could offer slightly higher accuracy on extremely complex or context-dependent queries (e.g., distinguishing "Axis bank" from "Axis fund"). However, this would come at the cost of **high latency**, **increased resource consumption** (CPU/GPU), and the significant overhead of creating a labeled dataset and **training the model**.
  * **Reasoning:** The rule-based approach delivers \>95% of the performance for \<5% of the complexity, making it the pragmatic and superior choice for this project's scope.

### 2\. Architecture: Modular (Separate Indexing) vs. Monolithic

  * **Decision:** The data ingestion and indexing pipeline (`build_index.py`) was completely separated from the runtime API server (`app.py`).
  * **Tradeoff:**
      * **Pros:** This creates a clean separation of concerns. The API server is **lightweight and starts quickly**, as it only loads pre-built indexes. This is a production-ready pattern that scales well. The indexing process can be run independently as a batch job.
      * **Cons:** The setup process is slightly more complex, requiring the user to run two separate commands (`python build_index.py` then `uvicorn app:app`). A monolithic approach where the server indexes on startup is simpler for a quick demo but is inefficient and not scalable.
  * **Reasoning:** The modular design is a best practice that makes the application more robust, efficient, and easier to maintain and deploy.

### 3\. Ambiguity Handling: Conversational vs. Direct Retrieval

  * **Decision:** When faced with vague queries or ambiguous entity names, the system was designed to **stop and ask the user for clarification** via a conversational loop.
  * **Tradeoff:**
      * **Pros:** This leads to **highly accurate and relevant answers**. The system never has to "guess" what the user means, which builds user trust. It makes the application feel more interactive and intelligent.
      * **Cons:** It adds an extra step for the user, increasing the time to get a final answer. A simpler approach would be to just perform a broad keyword search on the ambiguous query, but this would often return irrelevant or incomplete results.
  * **Reasoning:** For a financial assistant, accuracy and trustworthiness are paramount. Forcing clarification is far better than providing a fast but potentially incorrect answer.

### 4\. Database: Persistent (On-Disk) vs. In-Memory

  * **Decision:** Both the ChromaDB vector store and the BM25 index are saved to disk (`PersistentClient` and `pickle`).
  * **Tradeoff:**
      * **Pros:** This makes subsequent application startups **nearly instantaneous**. The expensive process of calculating embeddings and building the lexical index is only done once.
      * **Cons:** This approach uses disk space and introduces file I/O. For a very small, one-off script, an in-memory database might be slightly simpler to code, but it would be prohibitively slow for any real use case.
  * **Reasoning:** Persistence is essential for creating a responsive and efficient user experience.

## 🚀 Setup and Usage

1.  **Clone the Repository & Set Up Structure:**

      * Ensure your project directory is structured as described in the previous instructions.
      * Place your `faqs.csv` and `funds.csv` files in the `data/` directory.

2.  **Create Environment File:**

      * Create a `.env` file in the root directory.
      * Add your Groq API key: `GROQ_API_KEY="gsk_YourKeyHere"`

3.  **Install Dependencies:**

    ```bash
    # Create and activate a virtual environment
    python -m venv venv
    source venv/bin/activate # or .\venv\Scripts\activate on Windows

    # Install requirements
    pip install -r requirements.txt
    ```

4.  **Build the Indexes (One-Time Step):**

      * Run the indexing pipeline to create the persistent databases.

    <!-- end list -->

    ```bash
    python build_index.py
    ```

5.  **Run the API Server:**

      * Start the FastAPI application.

    <!-- end list -->

    ```bash
    uvicorn app:app --reload
    ```

6.  **Use the Application:**

      * Open your web browser and navigate to **`http://127.0.0.1:8000/`** to use the web interface.
